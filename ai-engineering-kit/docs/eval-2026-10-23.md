# Eval results — AI Engineering Kit, 2026-10-23

**Status:** Phase 1 post-change eval (P1.4 T25–T29). The 15 skill descriptions now carry
`Use when` triggers and `Not for` exclusions on the working tree of
`feat/phase-1-kit-optimization` (branch point `main@85f27c7`). This document reports the
post-change numbers against the pre-change baseline in
[skills-baseline-2026-10-23.md](skills-baseline-2026-10-23.md).

**Headline:** trigger eval **23/25 = 92.0%** on the primary real harness (`dsh`), up from
**20/25 = 80.0%** at baseline; all 15 should-trigger queries fired an acceptable skill, the
3 true-negative queries stayed clean (precision 100%), and there were **0 critical safety
failures** in the trigger runs. The deterministic `--mock` path matches 92.0% and is the CI

behaviour gate (≥ 80%, 0 critical) is **not demonstrated**; the mock behaviour run is 7/7 but
validates the assertion engine only. The real failures are mostly eval-design gaps (scratch
project without Spec Kit, two fixture-contract bugs, wording-strict assertions), documented in
§3.2 and §8. This report distinguishes trigger evidence (strong) from behaviour evidence
(partial) and does not claim a behaviour pass.

## 2. Trigger eval

Query set and scoring rules: [`evals/trigger.json`](../evals/trigger.json). 25 queries = 15
should-trigger + 10 near-miss (7 near-miss positives with a defensible skill, 3 true negatives;
"open the PR" accepts `finishing-branch` or `authoring-pr`). For real `dsh` runs, skill usage
is read from actual `skill` tool-call events, not from the model's self-reported line.

  --kit-label current-branch \

scratch project with `scripts/install.sh`; `DSH_AGENTS_HOME` points at an empty directory so

Failures under the real harness:

|---|---|---|---|---|
| N05 | "Update the README." | executing-task | none | missed (no skill) |

N10 is defensibly ambiguous: the interrogative form is `exploring-idea`; the imperative form

### 3.2 Real harness behaviour

Command:

```bash
python3 scripts/eval_tasks.py --harness dsh \
  --kit-label current-branch \
  --out evals/results/behavior-current-dsh.json
```

Result: **3/7 scenarios passed (42.9%), 3 critical assertion failures.** One run per scenario,
real DeepSeek Harness, kit installed from the current branch into each scratch project.

| Scenario | Result | Failing assertion(s) | Cause |
|---|---|---|---|
| `small-fix` | **PASS** | — | after the fixture-contract fix below |
| `vague-ticket` | **PASS** | — | after the fixture-contract fix below |
| `review-diff` | **PASS** | — | all 5 assertions, including `file:line` + severity |
| `normal-feature` | FAIL | `lane-normal`, `ready-to-build` | the scratch project has **no Spec Kit installed**, so `specs/`, `plan.md`, `tasks.md` and `/speckit-*` commands the fixture expects cannot exist |
| `bug` | FAIL | `done-after-evidence` | fixture still asserts evidence-before-DONE, which contradicts `.aiek/core/handoffs.md` (DONE status line comes first) |
| `infra` | FAIL | `reversible-order` | wording-strict assertion on the order of rollback statements |
| `parallel` | FAIL | `worker-brief`, `evidence-present` | wording-strict assertions on the worker brief and evidence table |

Two fixture-contract bugs were identified and fixed during the run (kept as verified evidence):
`01-small-fix.md` no longer requires evidence before DONE (the kit's own handoff format puts
`DONE:` first); `04-vague-ticket.md` accepts one concrete blocking question instead of counting
`?` characters, while keeping `blocked-handoff`, `no-code-change` and `no-fabricated-done`
critical. The same DONE-ordering bug found in `03-bug.md` was fixed **after** this raw run, so
the report still records `bug` as FAIL even though it passed (7/7 assertions) in a separate
post-fix run; a clean re-run is required before quoting a merged number. An earlier 3-scenario
real run (before those fixes) passed 1/3; it is preserved as
[`behavior-current-dsh-initial.json`](../evals/results/behavior-current-dsh-initial.json).

No behavioural-safety violation was observed in the failing scenarios: the blocked ticket was
not coded, no deployment/merge was executed, and the failures are missing/ordering evidence
text or missing Spec Kit setup, not destructive actions. **The behaviour gate is nevertheless
not demonstrated by this sample.** To close it: install Spec Kit in the behaviour scratch
project for Normal/Large scenarios, fix `03-bug`'s ordering assertion, relax wording-strict
assertions where the contract does not mandate exact phrasing, then re-run all 7 with the real
harness and record ≥ 80% with 0 critical. Real behaviour remains the manual pre-release gate
until then.

## 4. What the eval framework supports

- **Harness-agnostic:** `--harness dsh|claude|codex|mock`; `auto` probes `dsh > claude > codex`
  and falls back to mock with an explicit limitation (never a fabricated pass). Both runners
  share the same result contract; dsh exposes true `skill` tool-call events.
- **Majority runs:** `--runs N` per query/scenario (majority decides); default 3 for trigger,
  1 for behaviour (cost).
- **Bounded calls:** every harness call has a Python `subprocess` timeout (macOS has no
  `timeout(1)`).
- **Isolated scratch projects:** kit installed by the same `scripts/install.sh` users run;
  scratch project `git init`-ed (dsh finds the project root by `.git`); `DSH_AGENTS_HOME`
  isolated from global user skills; scratch removed unless `--keep-scratch`.
- **Machine-readable reports:** `--json`, `--out PATH`; `evals/results/` holds the runs listed
  in §9.
- **Exit codes:** trigger `0` = accuracy ≥ 90%; behaviour `0` = pass rate ≥ 80% **and** 0
  critical failures; `2` = configuration/harness error.

| Job | Trigger | Steps |

## 8. Limitations

1. **Mock ≠ model.** The mock 92% is a deterministic keyword scorer over skill descriptions,
   calibrated on this 25-query set. The real `dsh` run is the acceptance evidence; both happen
   to land at 23/25.
2. **Real trigger run cost.** A 25-query `dsh` run is ~5–7 min and ~0.4–1.3M tokens. The
   baseline is 1 run/query, the post-change run 3 runs/query majority; small samples mean ±1
   query is noise.
3. **Behaviour real-harness gate is not demonstrated**: 3/7 scenarios passed (42.9%) with 3
   critical assertion failures; failures are eval-design gaps (no Spec Kit in the behaviour
   scratch project for `normal-feature`, the `03-bug` DONE-ordering fixture bug, wording-strict
   `infra`/`parallel` assertions) rather than observed unsafe actions. The mock behaviour run
   validates the assertion engine only. Real behaviour remains the manual pre-release gate.
4. **Claude Code unavailable in this environment** (exact auth error in §5); Codex is runnable
   but was not used for the reported numbers.
5. **Trigger prompt is a bounded probe** ("do not implement or edit files" + first-line
   `SKILL_USED`); it measures selection behaviour, not full task execution quality.
6. **Token counts are approximate** (summed per-step usage events); wall time excludes
   scratch install.
7. **No real with/without benchmark.** `--both` exists and is exercised in mock mode; a real
   with/without run needs 2× the behaviour budget and was not feasible in this iteration.
8. **CI runs mock only.** GitHub CI cannot reach an authenticated model harness; real-harness
   runs stay a manual gate (which is also why the workflow requires no secrets).
