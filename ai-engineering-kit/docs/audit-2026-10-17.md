# Workflow audit — 2026-10-17

The architecture is worth keeping: one planner, a small execution skill set, and project facts
in an adapter. The defects are mainly conflicting instructions and missing proof at boundaries.
No replacement workflow, planning format, or custom orchestration engine is introduced.

Review covered every core document, skill/reference, Spec Kit component, adapter, and installer.
The directory was entirely untracked inside a parent repository. Changes were compared against
a pre-edit filesystem snapshot, not an empty Git diff. Unrelated sibling directories were untouched.

## Decisions retained or deferred

- **Keep all nine skills.** Debugging establishes cause; TDD builds a regression proof;
  verification establishes evidence; review evaluates correctness. Their outputs differ.
  Reducing the skill count would not itself solve ownership conflicts.
- **Keep Spec Kit planning and shaping's Feature Brief stop.** A brief is discovery input,
  not a parallel specification. No new planning artifacts were added to skills.
- **Deterministic unattended stopping remains open.** Concrete next fix: adopt a supported
  upstream structured stage-result gate, then test a BLOCKED result with process exit 0.
  Do not claim the current Markdown hooks provide that guarantee or fork the engine to add it.
- **Large workflow retains two explicit approval gates.** They are documented as deliberate
  supervised-runner checkpoints; interactive commands retain the conditional decision path.
  Removing them before structured stopping exists weakens the runner.
- **No skill renames or automatic Superpowers removal.** Global duplicate names/bootstrap
  activation need a real session-level inventory. The router now states which workflow owns
  planning; users should disable competing bootstrap workflows in that project/session.
- **Do not broaden supported versions from a render test.** Manifests now agree on their
  existing >=1.0.0 requirement; actual tests use recorded revision c6a4c18 (1.2.2.dev0).
  Oldest-version compatibility still needs a separate matrix before claiming it is proven.
- **Installer is not transactional.** Preflight catches known invalid inputs; a later upstream
  registration or filesystem error can still leave a partial install. It exits nonzero.
  `--force` still overwrites the adapter as documented: preserve local adapter edits before use.

The default machine CLI was 0.5.1.dev0; integration tests used a separate pinned upstream
checkout/environment. Initial sandboxed installer runs could not access the system temporary
directory; permitted reruns passed. No machine CLI upgrade was performed.

`test.py` covers dry-run/no mutation, invalid harness/no mutation, missing Spec Kit project,
repeat installation, project instruction and adapter preservation, symlink/copy behavior,
malformed marker rejection, and negative metadata/link/inventory/wrapper cases.
`test-speckit.py` checks real initialization and installation, preserved upstream content,
composed wrappers, rendered command references, extension commands, ordered mandatory hooks,
and registered workflows across the three advertised integrations.

These tests establish installation/rendering contracts, not agent behavior. Native Windows
execution, live subagent dispatch, human-review suspension/resume, and a complete agent-driven
feature lifecycle were not tested. Manual instruction review covered: trivial copy fix,
known/unknown-cause bugs, existing-spec ambiguity, task execution without subagents, Large work
without isolation, custom worktree directories, dirty worktrees, required human review, and
missing completion hooks. This is a consistency review, not an empirical model benchmark.
